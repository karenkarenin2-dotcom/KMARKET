## ГЛАВНЫЙ ФАКТ, из которого следует вся архитектура

**Blizzard API отдаёт ТОЛЬКО текущую цену жетона.** Эндпоинт
`/data/wow/token/index?namespace=dynamic-eu` возвращает две величины: `price`
(в меди) и `last_updated_timestamp` (в миллисекундах). Истории у Blizzard нет
вообще — ни за день, ни за час.

Отсюда: **сборщик важнее дашборда.** Дашборд можно переписать за вечер,
пропущенные часы истории не восстанавливаются ничем. Любое изменение,
затрагивающее сбор, оценивать по критерию «не может ли это молча остановить
сбор».

**Такт обновления — ровно 20 минут** (измерено 2026-07-22 на живых данных:
EU 11:02:44 → 11:22:44, US 11:01:32 → 11:21:32). У каждого региона своё
смещение внутри такта.

## КРОН ACTIONS — ЭТО ПОЖЕЛАНИЕ, А НЕ РАСПИСАНИЕ (измерено 2026-08-06)

Полтора года считалось, что `*/10` даёт две попытки на каждую точку. **Это
неправда.** Замер по накопленной истории:

| Что заказывали | Что получали |
|---|---|
| 144 запуска в сутки | 12–16 |
| 72 точки в сутки | **12.9** |

За 16 суток работы сборщика **потеряно 82% истории**, безвозвратно. Хуже
того, догоняющие залпы планировщика мы гасили сами: когда GitHub после
простоя выстреливал несколькими отложенными запусками разом, группа
`concurrency` отменяла все, кроме одного. В списке они видны как
`cancelled` с **нулём выполненных шагов** — это не падение, а отмена в
очереди, и по логам её легко принять за сбой сборщика.

**Лечение — окно, а не выстрел.** Сборщик получил `--minutes/--interval`:
проснувшись, он опрашивает API 55 минут подряд с шагом 5 минут, а workflow
коммитит пачками по ходу окна (не в конце — иначе смерть раннера на
сороковой минуте уносит всё окно). Отказ внутри окна цикл не прерывает;
красным запуск красится, только если не удалось НИ ОДНОГО опроса.

Из этого следует общее правило: **любой замер частоты сбора делать по
ДАННЫМ, а не по крону.** Крон врёт.

### `git pull --rebase` НА ПУТИ ДАННЫХ ЗАПРЕЩЁН (поломка 2026-08-07)

Частые коммиты сразу вскрыли следующую беду. Месячный CSV переписывается
ЦЕЛИКОМ и отсортированным; когда два запуска накладываются, обе стороны
переписывают один файл, и rebase упирается в конфликт **внутри данных**:

```
CONFLICT (content): Merge conflict in data/history/us/2026-08.csv
error: could not apply db74de9... data: 2026-08-07 12:39 UTC
```

Пока сборщик коммитил раз в 1–3 часа, столкнуться было почти не с чем.
С коммитами каждые 10 минут это стало обычным делом. И это тот же класс
аварии, что 2026-07-26: git норовит оставить маркеры конфликта в файле
с ценами.

**Лечение — не мержить, а переснимать.** В обоих workflow есть функция
`publish()`: проиграл гонку за push → `git reset --hard origin/main` и
повторный запуск сборщика на свежей базе. Цена жетона живёт 20 минут,
снимок аукциона дедуплицируется по времени Blizzard, поэтому пересъёмка
почти всегда возвращает ту же точку. Проверено на настоящей гонке двух
клонов: проигравший опубликовался со второй попытки, в облаке оказались
ОБЕ строки.

Правило на будущее: **сливать два полностью переписанных файла данных
git не умеет, и просить его об этом нельзя.**

## Как работать с этим проектом

- **ДО написания кода выпытывать у Карена ключевые решения короткими вопросами
  с вариантами** (процесс из KTOOLS, одобрен: «вопросы дешевле переделок»).
- Давать правки **цельными, готовыми версиями** — Карен смотрит результат глазами.
- Не изобретать визуальный язык — он уже есть (см. ниже и `../KARENIN_SITE/CLAUDE.md`).
- Секреты — только в `.env` (локально) и GitHub Secrets (в CI). В коде их нет.
  История: до 2026-07-22 ключи Blizzard лежали в `config.py` открытым текстом —
  файл удалён, секрет перевыпущен.
- **`.env` ПОБЕЖДАЕТ переменные окружения, а не наоборот** (баг, пойманный
  2026-07-23, стоил трёх алертов, ушедших чужому боту). `load_dotenv` раньше
  делал `setdefault`, и глобальная User-переменная Windows побеждала файл. У
  Карена в системе оказалась `TELEGRAM_BOT_TOKEN` от другого проекта
  (бот-напоминалка), и KMARKET молча слал в чужой чат, хотя `.env` был
  правильный и `sendMessage` возвращал `ok=true`. `.env` — явная конфигурация
  этого проекта, окружение — общая свалка; поэтому файл главнее, а расхождение
  печатается предупреждением, не проглатывается. В CI `.env` нет — там
  Secrets через окружение, случай не затронут.

**`kmarket/web/` больше нет.** FastAPI + uvicorn + браузер заменены окном
на WebView2 (решение Карена 2026-08-06): приложению не нужен ни порт, ни
сервер, ни вкладка среди прочих вкладок, ни второй способ запуска.

`CLAUDE.md` ОБЯЗАН лежать в корне: Claude Code подхватывает его автоматически
только оттуда, из `docs/` он не читается. Поэтому здесь — полная выжимка
решений и ловушек, а в `docs/` — то же самое человеческим языком и подробнее.

- **Сборщик обязан работать на голой стандартной библиотеке.** `pip install`
  в Actions — это лишняя минута на каждый из ~4400 месячных запусков и лишняя
  точка отказа из-за чужого релиза. Зависимости (pandas, FastAPI) нужны только
  локальному дашборду. Это правило не нарушать даже ради удобства.
- **Опрашиваем каждые 10 минут, хотя цена меняется ~раз в 20.** Крон в Actions
  не гарантирует точность: в пиковые часы запуск задерживается или пропускается.
  Лишние опросы бесплатны (дубли отсеиваются по `updated_utc`), пропуск — нет.
- **CSV, а не база.** Читается глазами, дифается в git (репозиторий и есть
  хранилище), год замеров ≈ 52 тыс. строк — для pandas ничто. База потребовала
  бы хостинга, то есть денег и ещё одной точки отказа.
- **Дедупликация по `updated_utc`** — времени самой Blizzard, не времени опроса.
- Месячный файл всегда переписывается целиком отсортированным (через `.tmp` +
  атомарный `replace`): на 4-5 тыс. строк мгновенно, а git видит diff в одну строку.
- **Ненулевой код возврата у сборщика** при отказе API — обязателен: молча
  вставший сбор не восстановить.
- **У каждого файла данных ОДИН писатель.** `data/history` принадлежит
  облачному сборщику, `data/live` — локальному дашборду, и она в `.gitignore`.
  Нарушение этого правила стоило поломки 2026-07-26 (см. ниже).

## ПОЛОМКА 2026-07-26 — три урока, которые не повторять

Дашборд падал с `TypeError: int() argument must be ... not 'NoneType'`, а в
консоли висело «История не обновлена». Причина оказалась цепочкой из трёх
моих ошибок, и каждая по отдельности безобидна:

1. **Два писателя в один файл.** `live.py` дописывал живые цены прямо в
   `data/history`, поэтому рабочее дерево всегда было «грязным».
2. **Автопулл с заначкой.** `git pull --rebase --autostash` в `web/__main__.py`
   прятал эти правки, перебазировался и не мог вернуть заначку — и вписывал
   `<<<<<<<` / `=======` / `>>>>>>> Stashed changes` **ВНУТРЬ CSV с данными**.
   Git застревал в состоянии `UU`, последующие `git pull` отказывались работать.
3. **Хрупкий парсер.** `read_month` ловил только `KeyError`/`ValueError`, а у
   строки-маркера нет второго поля → `int(None)` → `TypeError`, и ОДНА битая
   строка уносила весь дашборд.

Лечение (все три предохранителя нужны, не убирать ни один):
`data/live` вне git · `git pull --ff-only` (fast-forward физически не может
испортить рабочие файлы) · `read_month` глотает и `TypeError`.

**Побочный урок про диагностику:** проверка маркеров через
`Select-String -Pattern '^<<<<<<<' -SimpleMatch` НЕ РАБОТАЕТ — `-SimpleMatch`
отключает regex, и `^` ищется как литерал. Из-за этого первая проверка
показала «маркеров нет», хотя они были. Regex-поиск без `-SimpleMatch`.

## НАЙДЕНО НА ДАННЫХ (2026-07-22) — не переоткрывать заново

### 1. Жадность проигрывает: порог 30 лучше порога 5

`backtest.stockpile` на 5 полных годах EU, профиль «набрать N жетонов за год»:

| Жетонов/год | Лучшее правило | Экономия |
|---|---|---|
| 6 | окно 90, порог **30** | 13.7% |
| 12 | окно 60, порог **30** | 11.7% |
| 24 | окно 90, порог **30** | 9.3% |

Порог 5-го перцентиля проигрывает ВЕЗДЕ. Причина — поле `forced_buys`:
строгое правило срабатывает редко, годовую норму набрать не успеваешь и
докупаешь в конце года по любой цене. Отсюда `BUY_PERCENTILE = 30`.

### 2. Эффект ресета: внутри недели разброс ~8%

Сезонность по времени серверов (6692 точки за год):

- **Дороже всего:** Ср 05:00 (+5.3%), Вт 07:00 (+5.25%), Вт 04:00 (+5.04%)
- **Дешевле всего:** Сб 12:00 (−2.43%), Вс 13:00 (−2.32%), Пт 12:00 (−2.11%)

Это недельный ресет EU (ночь со вторника на среду): перед ним массово
скупают жетоны за золото. Выбор дня недели даёт до 8% — сопоставимо со
всей стратегией перцентилей. По дням: Вт +1.5%, Ср +1.1% против Сб −0.33%.

### 3. Пойманная ошибка метрики: база сравнения в трендовом рынке

Первая версия бэктеста сравнивала цену покупки со СРЕДНЕЙ ЗА ВЕСЬ ПЕРИОД
и показывала «экономию 12.4%» для правила 180/5. Это был артефакт: цена
выросла со 153 тыс. (2020) до 370 тыс. (2026), поэтому любое правило
«покупай дёшево» срабатывает преимущественно в ранние дешёвые годы, и
«экономия» означала «купил в 2021-м», а не «хорошо выбрал момент».

Лечение — сравнивать только ЛОКАЛЬНО: `local_advantage_pct` (±45 дней
вокруг той же даты) и `stockpile` (сравнение внутри одного года). Урок
общий: **в трендовом ряду любая метрика с глобальной базой льстит.**

### 4. Такт Blizzard и расхождение регионов

- Цена пересчитывается ровно раз в 20 минут, у каждого региона своё смещение.
- На 2026-07-22 EU стоял на 50-м перцентиле за 30 дней, US — на 96-м.
  Регионы могут расходиться сильно; гипотезу «US опережает EU» проверять
  корреляцией со сдвигом, на веру не брать.

### 5. САМЫЙ СИЛЬНЫЙ СИГНАЛ: фаза игрового события (размах 30%)

Наблюдение Карена («патчи сильно влияют на цену») проверено событийным
анализом по 18 событиям (`events.study`, нормализация к медиане окна ±30
дней — без неё «эффект патча» выродился бы в «цена за 5 лет выросла»):

| Событие | 30..8 дн ДО | ±7 дн | 8..30 дн ПОСЛЕ | Размах |
|---|---|---|---|---|
| Запуск дополнения (3) | **+12.0%** | +0.4% | **−11.8%** | **30.3%** |
| Старт сезона (12) | +6.9% | +0.3% | −5.0% | 16.7% |
| Пре-патч (3) | +0.7% | +2.5% | −3.0% | 10.2% |

Направление ОДИНАКОВО во всех типах: перед событием цена задрана, после
обваливается. Механика — перед стартом контента массово покупают жетоны
за золото под подготовку.

**Это сильнее всего остального, что мы нашли:** 30% против 11% у стратегии
перцентилей и 8% у недельной сезонности. Поэтому `verdict._event_reason`
имеет право ПЕРЕБИВАТЬ перцентиль — но только в сторону осторожности
(словарь `CAUTION`): «дёшево за неделю до запуска» и «дёшево через месяц
после» — это разные «дёшево».

### ЧАСТЬ ДАТ НАХОДИТСЯ САМА (уточнено 2026-08-08)

Прежняя запись «Blizzard не отдаёт даты через API — автоматизировать
нечем» оказалась неверной. Отдельного эндпоинта действительно нет, но
нужное лежит в двух местах (`kmarket/gameinfo.py`):

1. **Версия сборки** зашита в `namespace` любой статической ссылки:
   `static-12.0.7_67808-eu`. Смена мажор.минор (12.0 → 12.1) — это выход
   контентного патча. Хотфиксы (12.0.7 → 12.0.8) намеренно игнорируются.
2. **Старт сезона** — `/data/wow/mythic-keystone/season/{id}` отдаёт
   `start_timestamp`. Проверено: сезон 17 начался 2026-03-18, тогда как
   в ручном списке стояло 17 марта. API точнее, ему и верим.

Найденное копится в `data/game_state.json` и подмешивается к ручному
списку через `events.all_events()`; при совпадении даты и вида побеждает
ручная запись — у неё человеческое название.

**ЧТО ЭТО НЕ ЧИНИТ.** Обнаружение всегда ПОСТ ФАКТУМ: API говорит «патч
уже вышел», а не «выйдет через неделю». Автоматика закрывает фазу ПОСЛЕ
события, а фаза ДО — самый ценный сигнал, +12% за месяц до запуска —
по-прежнему требует внесённой руками даты. Анонсы живут в новостях.

Поэтому есть `events.staleness()`: если в календаре не осталось будущих
дат ближе `STALE_HORIZON_DAYS`, алерт раз в неделю напоминает пополнить
список. Молчаливое протухание превращено в громкое — полностью починить
его нечем.

**Грабля первого запуска.** `"".split(".")` возвращает `['']` — НЕПУСТОЙ
список, и первая версия проверки на пустое прошлое состояние его
пропустила. Сухой прогон честно доложил «вышел патч 12.0», хотя он вышел
месяцами раньше. Первый запуск обязан только запоминать базу, ничего не
объявляя.

## МОДУЛЬ 2: ТОВАРНЫЙ АУКЦИОН (сделано 2026-08-06)

Эндпоинт `/data/wow/auctions/commodities?namespace=dynamic-eu` — расходники
и реагенты сразу по всему региону, реалм не важен. Замер на живом ответе:
**265 608 лотов, 12 022 предмета, 2.9 МБ в gzip (24.8 МБ распакованных),
скачивание 1.2 с.** Обычные лоты (шмот, петы, маунты) живут по связанным
реалмам отдельными снимками — осознанно не берём.

**Такт — ЧАС**, не 20 минут. Поэтому у аукциона свой сборщик
(`collect_auction.py`) и свой workflow (`auction.yml`): смешав их с
жетоном, мы либо качали бы 3 МБ каждые десять минут впустую, либо
проредили бы жетон.

### Четыре грабли, каждая проверена на живом ответе

1. **urllib не шлёт `Accept-Encoding: gzip` сам** — восьмикратная разница
   в трафике. И, попросив gzip, **распаковывать надо тоже самому**: urllib
   отдаёт тело как есть. Опознаём по сигнатуре `1f 8b`, а НЕ по заголовку:
   Blizzard шлёт его строчными (`content-encoding`), и `dict(headers)`
   теряет регистронезависимость.
2. **Ретраи обязательны, но НЕ на 4xx.** Самый первый запрос к commodities
   вернул случайный HTTP 500. Но справочник намеренно пробует
   несуществующие соседние ID, и ретраи на 404 стоили по 6 секунд сна
   (2с + 4с) на каждую пробу — это один раз подвесило сборку списка
   насмерть. Теперь 4xx (кроме 429) пробрасывается сразу.
3. **Ранжировать по `сумма(кол-во × цена)` НЕЛЬЗЯ.** Первый прогон вывел в
   топ «Почти свинину» с оборотом 23 млрд золота: на аукционе всегда висят
   одиночные лоты по конской цене, и в сумме они перевешивают весь
   реальный рынок. Считаем по НИЖНИМ 15% предложения (`MARKET_SHARE`).
4. **Фильтр мусора обязателен, и по ЧИСЛОВЫМ id вида, не по названиям.**
   Без фильтра в топ лезут «Сломанный тяжелый метательный кинжал» по 325
   тыс. золота и «Обломок доспехов» — ванильный хлам и квестовые предметы,
   которых на весь EU по две сотни штук. Отсекаются глубиной рынка
   (`MIN_QUANTITY`, `MIN_LOTS`), а не ценой. Фильтровать по русским
   «Хлам»/«Задание» нельзя — они зависят от `locale`.

### Ранги качества ремесла: API их НЕ отдаёт

Реагенты с Dragonflight выпускаются в нескольких качествах, и у них
**разные ID при полностью совпадающих карточках** — проверено на 242620 и
242621: одинаковы имя, качество, описание, даже файл иконки. Единственная
зацепка — поле `modified_crafting`: у ранговых оно есть и содержит общий
`category.id`. Внутри группы ранги идут **подряд по возрастанию ID**
(Кровотерн 236770/236771, Азефит 236774/236775, Сребревица 236776/236777,
Маналилия 236778/236779, пыль 242620/242621). Ранг = позиция в
отсортированной группе.

**Количество рангов РАЗНОЕ и числом его зашивать нельзя.** В собранном
справочнике из 172 ранговых предметов 118 живут группами по два, а 54 —
по три. У реагентов Midnight обычно два, у наследия Dragonflight три.
Код считает размер группы, а не предполагает его.

Группу нельзя собирать только из попавших в наш список предметов: если в
топ вышел лишь ранг 2, он получит подпись «ранг 1 из 1», тихо неверную.
Отсюда проба соседних ID (`NEIGHBOURS`).

### ШИРОКИЙ СРЕЗ ПОД ПАТЧ 12.1 — ВРЕМЕННАЯ МЕРА СО СРОКОМ

Часовая слежка идёт по списку из 400 товаров, отобранных по ликвидности
ДО патча. Новых реагентов Coiled Isle в этом списке физически нет — их
ещё не существует. Записать рынок целиком через запуск сезона можно
только пока это происходит: истории у Blizzard нет, прошлое не
отматывается.

Поэтому на цикл патча включён `--wide-hours 6`: весь аукцион, все ~12
тысяч предметов, четыре раза в сутки, в `data/auction_wide/<регион>/
<ГГГГ-ММ-ДД>.csv`. Замерено: **0.56 МБ на срез, 2.3 МБ в сутки, 59 МБ за
26 дней.**

Устройство отличается от узкой истории намеренно:
- **файл на СУТКИ, не на месяц** — месячный весил бы полтора миллиона
  строк, и переписывать его целиком на каждом срезе стало бы дорого;
- **дозапись, а не переписывание** — срезы приходят по возрастанию
  времени, файл и так упорядочен, git видит diff в хвост;
- **полей меньше** (нет глубины хвоста) — для вопроса «что подорожало
  вокруг патча» она не нужна, а вес поднимает на треть.

**У меры зашит срок — `WIDE_UNTIL` в `collect_auction.py`.** Временные
меры никто не выключает руками, их забывают; через год выяснилось бы,
что репозиторий распух на десятки гигабайт. Срок стоит в КОДЕ, а не
только в комментарии к workflow. Продлевать — осознанно меняя дату.

### Чего у аукциона нет и не будет

**Внешнего архива не существует.** Жетону когда-то залили бутстрап с 2020
года; по commodities заливать неоткуда. Копим с нуля, и перцентили
заработают через недели. Модуль обязан честно говорить «истории мало»
(`MIN_POINTS`), а не рисовать уверенный уровень по трём замерам —
выдуманная точность на деньгах опаснее отсутствия ответа.

Зато **разрыв «пол против рынка» работает с первого снимка** и истории не
требует: если самый дешёвый лот сильно ниже цены выкупа нижних 15%
предложения, кто-то сливает товар. Это и есть «недооценённые».

### ЦЕНАМ ИЗ СНИМКА ВЕРИТЬ МОЖНО, КОЛИЧЕСТВУ — НЕТ (измерено 2026-08-08)

Карен сверил приложение с настоящим прилавком в игре: у нас «скупить всё
5 187 з», в игре — 39 804 з. Расчёт был верен, расходились исходные
данные. В снимке Blizzard лежало 25 414 дешёвых единиц «Сущности
маназмея», а в игре уже 183 820: кто-то вывалил хвост ПОСЛЕ того, как
Blizzard сделала слепок. Такт слепка — час, обойти нельзя, у всех
трекеров он тот же.

Замер по 32 снимкам, медиана изменения между соседними часами:

| Показатель | Дрейф |
|---|---|
| цена, пол | 0.3% |
| цена после | 0.0% |
| общий запас | 2.5% |
| **дешёвый хвост (`deal_qty`)** | **19.8%**, у 23% товаров больше 50% |

Отсюда правило показа: **цены — факт, количество и производные от него
(`deal_cost`, `upside_gold`) — оценка порядка величины.** В окне стоит
возраст снимка и оговорка об этом. Софт не врал, но и не предупреждал, а
выдавать оценку за факт нельзя — по ней тратят золото.

Заметь, что ошибка тут двусторонняя и в этот раз была В ПОЛЬЗУ Карена:
дешёвых лотов оказалось в семь раз больше обещанного. Сама возможность
была настоящей.

### ЭТО НЕ СНАЙПИНГ, А МАРШРУТ (измерено 2026-08-08)

Из часового такта следует важный вывод о самой стратегии. Гнаться за
конкретным дешёвым лотом мы НЕ МОЖЕМ: к моменту покупки его состав уже
другой, и против аддонов в игре, видящих рынок живьём, мы структурно
медленные. Это не чинится.

Зато можно ответить на вопрос, от скорости не зависящий: у этого товара
скидка — постоянное свойство рынка или разовая случайность? Замер по 32
снимкам:

| | Текущее дополнение (158) | Старьё (251) |
|---|---|---|
| разрыв почти всегда (>90%) | **0** | 48 |
| разрыв чаще половины времени | **12** | 42 |
| разрыв изредка | 146 | 161 |

У текущего дополнения постоянного разрыва нет ни у кого — рынок съедает
дешёвые лоты за минуты. Но у ДВЕНАДЦАТИ позиций он есть больше половины
времени («Фантомник» и «Гуппи-живодёр» 88%, «Закаленная Бездной
пластина» 72%). Это и есть рабочая стратегия: не «успеть за пять минут»,
а «вот дюжина мест, куда заходишь регулярно, и примерно в каждый второй
раз что-то есть».

Отсюда метрика `_gap_rate` — доля прошлых снимков, где разрыв был. Она
стоит в строке товара и поднимает постоянные находки над разовыми:
разовая удача с большим наваром не должна вытеснять маршрут, по которому
можно ходить каждый день.

### РАЗВОРОТ: АРБИТРАЖ НАМ НЕДОСТУПЕН, ТОРГУЕМ ЦИКЛОМ (решение Карена 2026-08-09)

Карен проверил находки на живом прилавке дважды, и оба раза счёт был не в
нашу пользу. Второй случай — приговор всей ветке выкупа хвостов:

| «Искаженная ведуница» | наш снимок (24 мин) | в игре |
|---|---|---|
| пол | 12.00 з | **16.98 з** |
| всего в продаже | 4 069 шт | **12 748 шт** |
| дешёвый хвост | 600 шт по 12–14.5 з | **съеден подчистую** |

За двадцать четыре минуты хвост разобрали, а сверху навалили 10 477 шт по
17.50. **Сделка перестала существовать раньше, чем её успели прочитать.**

Снимок commodities обновляется раз в ЧАС — у всех, включая нас. Аддоны в
игре видят прилавок живьём. Это не отставание, которое сокращают, а другая
весовая категория; Карен назвал это «боремся с ботами». Запись «это не
снайпинг, а маршрут» (2026-08-08) была верной наполовину: даже постоянный
разрыв к приходу уже съеден.

**Отсюда разворот, и он не про метрику, а про стратегию.** Позиционная
торговля циклом патча скорости не требует: держишь реагент две недели
через старт сезона — часовой лаг меньше погрешности. И она опирается на
самый сильный сигнал, какой в проекте измерен: фаза события, размах 30%
против 11% у перцентилей и 8% у недельной сезонности. На реагентах он
должен быть сильнее, чем на жетоне: жетон покупают за золото, а реагенты
ПОТРЕБЛЯЮТ, и потребление привязано к контенту.

Формулировка Карена: «В конце сезона гелиотроп не нужен никому, все давно
оделись. К старту нового он нужен всем сразу». Аудитория — рейдеры и
ключники; PvP добавляет всплеск, но объём спроса дают не они.

Ветку «недооценённые» не удалять, но с главного места убрать и подписать
честно: это лотерея, в которой мы медленные.

### СПИСОК СЛЕЖКИ ПО РОЛИ, А НЕ ПО ОБОРОТУ (2026-08-09)

Автоподбор ранжировал по обороту и отвечал на вопрос «где много торгуют».
Нужен ответ на другой — «что людям НУЖНО».

`kmarket/recipes.py` выгружает реагенты из рецептов профессий текущего
дополнения: 13 профессий, 937 рецептов, **63 реагента** с весом по числу
рецептов и суммарному количеству. Тиры находятся по слову `Midnight` в
названии (`CURRENT_TIER_MARK`); ноль найденных профессий — громкий отказ,
а не тихая работа на прошлом дополнении.

Проверка окупила затею сразу: **27 реагентов из 63 в слежке ОТСУТСТВОВАЛИ**,
и среди них «Талассийская древесина» (60 рецептов), «Сияющий плавень» (56),
«Гибкий проволочный каркас» (54), «Крученая вышивальная нить» (45). Отбор
по обороту их не видел.

`watchlist.role_ids()` подмешивает роль прямо в `item_ids()`, а не только
при месячной пересборке: реагент, попавший в сбор после подорожания,
бесполезен — история должна начаться ДО.

**ЧАСТОТА В РЕЦЕПТАХ НЕ РАВНА СПРОСУ.** «Зачарованный гелиотроп» входит
всего в три рецепта ювелирки, но крафтят их все и на каждый слот. Поэтому
роль решает, СЛЕДИТЬ ли за предметом, а важность считается по рынку.

**ЧЕГО В API НЕТ.** Поля `crafted_item` у рецептов Midnight нет ни у
одного из 52 проверенных — что получается на выходе, придётся связывать
по названию. И реагенты слотов качества (`modified_crafting_slots`)
задаются КАТЕГОРИЕЙ, а `/modified-crafting/category/{id}` отдаёт только
имя без состава: связь идёт со стороны предмета, через его поле
`modified_crafting`. Собранные 63 — это фиксированные реагенты.

### ОСНОВНОЕ СЫРЬЁ ЛЕЖИТ В СЛОТАХ, А НЕ В СОСТАВЕ (2026-08-09)

Первый сбор дал 63 реагента и выглядел полным. Он не был полным: у 566
рецептов из 586 в `reagents` лежит одна-две позиции, а всё остальное
игрок кладёт в `modified_crafting_slots`. У «Поющей шестеренки» видимого
сырья — один каркас, плюс три слота (медная руда, оловянная руда, почерк
ремесленника).

**В слоте есть ИМЯ реагента, но нет КОЛИЧЕСТВА.** Имя разрешается точным
поиском: из 69 имён слотов 53 оказались настоящими предметами, остальные
16 — описания («Наполняет силой», «Позволяет указать второстепенные
характеристики»), и отсеиваются они сами тем, что не находятся. Вручную
такой список вести нельзя — он меняется каждое дополнение.

Роль выросла с 63 предметов до **115**, слежка — до 446. Появилось то,
чего не было ни в отборе по обороту, ни в фиксированных составах:
«Вечнопоющая пыль» (80 рецептов), «Сумрачный сплав» (49), «Кристалл
зари» (47), «Луносветская окантовка доспеха» (45).

**ГРАБЛЯ, НА КОТОРОЙ Я УЖЕ ПОСКОЛЬЗНУЛСЯ.** Слотовое сырьё попало в
слежку, но список «что запасать» его не показывал: фильтр смотрел только
в `reagents`. Источников роли ДВА (`analytics/auction._roles`), и забыть
второй — значит собирать данные и не пользоваться ими.

### КРАФТ-МАРЖА ПО API НЕ СЧИТАЕТСЯ — ЗАКРЫТО (2026-08-09)

Итог разбора, чтобы не открывать заново:

| | |
|---|---|
| рецептов с найденным изделием | 586 из 602 |
| из них со слотами качества | **566** |
| осталось с полностью известным сырьём | 20 |
| из них: изделия нет на commodities | 16 |
| крафт убыточен | 4 |
| **пригодных** | **0** |

Количество сырья в слотах не сообщается НИГДЕ — ни в рецепте, ни в
слот-типе, ни в категории. Снаряжение вдобавок торгуется на реалмовых
аукционах, которых мы не собираем.

**И ГЛАВНЫЙ УРОК, ТОТ ЖЕ САМЫЙ В ТРЕТИЙ РАЗ.** Сначала такие рецепты
просто помечались флагом «сырьё неполное» и всё равно показывались.
Первый прогон вывел «Подкладку из тайной ткани» с наваром **407
МИЛЛИОНОВ** золота: из трёх слотов не посчитан ни один, видимого сырья
на 0.07 з. Все двенадцать верхних строк были такими же.

Метрика систематически поднимает наверх записи с САМОЙ БОЛЬШОЙ дырой в
данных — как «навар от выкупа всего хвоста» поднимал самые большие кучи.
**Флаг рядом с числом не спасает: чем неполнее данные, тем выше строка.**
Неполные записи надо выбрасывать из расчёта, а не помечать.

### КРАФТ-МАРЖА: ЕДИНСТВЕННЫЙ СИГНАЛ, ГДЕ СКОРОСТЬ НЕ НУЖНА (2026-08-09)

Выкуп хвоста требует успеть раньше других — там мы структурно проигрываем.
Крафт-маржа устроена иначе: это разница между ДВУМЯ рынками, сырья и
изделия, и закрывает её производство, а не один быстрый покупатель.
Поэтому она держится часами и часовой лаг снимка ей не мешает.

**Связь «рецепт → изделие» приходится добывать самим.** Поля
`crafted_item` у рецептов Midnight нет ни у одного. Зато имя рецепта
совпадает с именем предмета — целиком или после двоеточия
(«Трансмутация: частица дикой магии»). Точный поиск
`/data/wow/search/item?name.ru_RU=` связал **586 из 602** рецептов.

**Брать только ТОЧНОЕ совпадение имени.** Поиск Blizzard нечёткий: на
«Зачарованный гелиотроп» он выдаёт сотню предметов начиная с
«Зачарованного агата». Первый результат привязал бы маржу к цене чужого
предмета, и ошибка была бы тихой.

**СЕБЕСТОИМОСТЬ СЧИТАЕТСЯ ПО `market`, А НЕ ПО ПОЛУ.** Закупая сырьё
мешками, ты выметаешь дешёвые лоты и платишь примерно по уровню
восстановления. Пол польстил бы ровно так же, как «цена после» льстила в
расчёте перекупки, — та же ошибка в другом месте.

**ДВЕ ДЫРЫ, КОТОРЫЕ ПОМЕЧАЮТСЯ, А НЕ ЗАМЕТАЮТСЯ:**

1. У рецептов со **слотами качества** в `reagents` лежит лишь часть
   сырья: слот задаётся категорией, состав которой API не отдаёт. Значит
   настоящая себестоимость ВЫШЕ, а выгода ниже показанной. Такие рецепты
   несут флаг `partial` и метку в интерфейсе. Занижать себестоимость
   опаснее, чем промолчать: по завышенной выгоде тратят золото.
2. **Снаряжение не попадает в расчёт вовсе** — оно торгуется на реалмовых
   аукционах, которых мы не собираем. Покрываются расходники, чары, камни
   и еда.

### МЕТРИКА НАХОДОК ИСКАЛА САМУЮ БОЛЬШУЮ КУЧУ (исправлено 2026-08-09)

Карен потестил на живом рынке и вынес вердикт: «товары, которые советует
софт, по факту оказываются огромных объёмов. Пока ты их будешь продавать,
появятся новые, которые перебьют тысячи наших. Другие люди орудуют
тысячей, а мы пытаемся сбыть сорок тысяч».

Это не промах отбора, а **целевая функция**. Выгода считалась как
`deal_qty × market − deal_cost` — навар от выкупа ХВОСТА ЦЕЛИКОМ. Величина
линейна по количеству, поэтому товар с 40 тыс. единиц и маржой 3% всегда
обгонял товар с 200 единицами и маржой 60%. Софт добросовестно
оптимизировал размер кучи. Плюс никто ни разу не спросил, сколько у
Карена золота: предлагались операции на 2.2 млн.

**Теперь считается СДЕЛКА, а не стакан** (`analytics/auction._plan`).
Банк — 50 тыс. з на позицию (`BUDGET_GOLD`, решение Карена), горизонт
оборота — сутки (`HORIZON_HOURS`). Размер равен самому узкому из трёх
пределов: кошелёк, сбыт (`net × horizon − wall_qty`), наличие в хвосте.
Порядок находок — по **прибыли в час**, делённой на срок сделки: 40 тысяч
единиц, расходящихся неделю, проигрывают двум сотням, уходящим к вечеру.

Для этого в `Quote` появились **ступеньки хвоста** (`deal_book`): двух
итоговых чисел хватало ровно на один сценарий «выкупить всё», а под
бюджет нужен сам стакан. В CSV не пишутся, живут в памяти снимка —
приложение и так запрашивает аукцион живьём.

**Очередь меряется от ТВОЕЙ покупки, а не от всего хвоста.** Старый
`wall_ratio` делил стену на `deal_qty` и потому промахивался там, где
нужен был больше всего: у «Кель'таласского филе» впереди стояло 154 352
шт, но хвост был ещё больше, отношение выходило меньше тройки — и товар
шёл в находки ПЕРВЫМ номером. Относительно реальной покупки очередь
оказалась вчетверо длиннее. После правки предохранители отсеивают 85
товаров из 400, а размеры покупок упали с десятков тысяч штук до сотен.

### ПРОДАЁШЬ ПО ТОЙ ЦЕНЕ, ДО КОТОРОЙ ДОТЯНУЛСЯ ВЫКУП (2026-08-09)

Карен принёс скриншот прилавка, и он вскрыл ошибку в самой основе расчёта.
Софт советовал «Рысевку»: взять 2 246 шт за 50 тыс. и продать по 37.42 з
(«цена после»). В игре это неисполнимо, и вот почему.

| | |
|---|---|
| пол | 21.97 з |
| «цена после» (граница 15% предложения) | 37.42 з |
| чтобы пол ДОШЁЛ до 37.42, выкупить надо | 14 886 шт за 381 253 з |
| на 50 тыс. выкупается | ~2 250 шт, пол сдвигается до 22.19 з |

**Выкупив часть дешёвых лотов, ты не поднял пол** — под тобой остались
чужие, и покупатели уйдут к ним. Значит перепродать можно только по цене
ступеньки, на которой ВЫКУП ЗАКОНЧИЛСЯ, а не по «цене после».

Пока выкупался хвост ЦЕЛИКОМ, формула `deal_qty × market − deal_cost` была
верна: тогда пол действительно поднимается до `market`. Ошибкой было
распространить её на частичный выкуп — это сделал я, вводя бюджет, и
сломал внутреннюю согласованность метрики: до правки она была
неисполнимой по деньгам, после — неисполнимой логически.

Теперь `_stops` перебирает ГРАНИЦЫ ступенек стакана: остановился перед
ступенькой — выкупил всё, что дешевле, новый пол равен её цене, по ней и
продаёшь, встав в очередь к тем, кто на ней стоит. Выбирается граница с
лучшей прибылью в час. Частичный выкуп ступеньки бессмыслен: пол остаётся
на её цене, а купленные по ней единицы приносят минус комиссию.

**Побочное следствие — то самое лекарство от жалобы Карена.** Товар с
толстым дешёвым хвостом теперь честно говорит «на этот бюджет пол почти
не сдвинется» и уходит из находок сам, без отдельных предохранителей: на
доступные деньги пол двигается на копейки, и комиссия съедает остаток.
Наверх поднимаются товары с ТОНКИМ хвостом и резкой ступенькой — те, где
выкуп по карману целиком.

Та же поправка внесена в `_gap_rate`: в истории ступенек нет, поэтому там
засчитываются только снимки, где хвост был дешевле банка, — единственный
случай, когда старая формула честна.

**Общее правило: любая метрика перекупки обязана называть цену, которая
ДОСТИЖИМА на твои деньги.** Цена из снимка — не обещание.

### ПОДРЕЗАНИЕ ИЗМЕРИМО ТЕМ ЖЕ СПОСОБОМ, ЧТО ПРОДАЖИ (2026-08-09)

Продажи отвечают на вопрос «уходит ли товар» и молчат о главном: достанется
ли выручка ТЕБЕ. Перекупщик живёт на разнице между тем, как быстро
разбирают, и тем, как быстро подвозят новое дешёвое. Если подвозят
быстрее — очередь не рассосётся никогда, сколько бы ни продавалось.

`auction.added_between` — зеркало `sold_between`: новые id лотов, вставшие
НИЖЕ уровня восстановления. Поле `added_qty` в CSV, `_restock_rate` в
аналитике, и вся арифметика сделки идёт по ЧИСТОЙ скорости
`net = sold − restock`. При `net ≤ 0` сделки нет ни при какой марже.

### ИЗМЕРЕНИЕ ПРОДАЖ НЕ РАБОТАЛО ВОВСЕ (найдено 2026-08-09)

Проверка по накопленным данным: за двое суток **42 снимка и РОВНО ДВА
измерения** продаж, ни у одного из 409 товаров не набралось минимума в
четыре. То есть `hours_to_clear` всегда был `None`, и предохранитель
«разойдётся за N часов», написанный после истории с «Сущностью маназмея»,
существовал в коде и молчал в жизни.

Причина: Blizzard обновляет commodities около **41-й минуты часа**
(подтверждено живыми снимками 08:41, 14:41, 15:41), крон стоит на :07 и
:37, отрезок сборщика длится 30 минут, а прошлый снимок жил только в
памяти процесса. Граница часа попадала внутрь отрезка, лишь когда тот
стартовал в подходящие полчаса.

Лечение — `--state`: лоты передаются следующему отрезку через файл в
`RUNNER_TEMP`. Не в git (17 тыс. id каждый час — мегабайты мусора), потеря
файла ничего не ломает.

**Урок тот же, что с кроном: проверять по ДАННЫМ, а не по замыслу.**
Механизм был написан правильно, включён везде, где надо, и не работал.

### БОЛЬШОЙ СПРЕД — ЧАЩЕ ЛОВУШКА, ЧЕМ НАХОДКА (измерено 2026-08-07)

Состав первого списка находок: **9 из 11 — товары СТАРЫХ дополнений**.
У товаров текущего (Midnight) доходность выкупа всего 2.5–7.8%.

Причина не случайна и повторится: текущее дополнение смотрят все, там
рынок эффективный и дешёвые лоты разбирают за минуты. Большой спред на
старом товаре существует ИМЕННО ПОТОМУ, что его рынок никто не мониторит,
— и по той же причине перепродать выкупленное может быть некому. То есть
метрика «навара» сама по себе тащит туда, где риск застрять максимальный.

Отсюда два предохранителя, оба обязательны:

1. **Метка эпохи** (`CURRENT_ERA_FROM_ID`, ID ≥ 236000 — Midnight).
   Способ приблизительный, принадлежность к дополнению Blizzard не отдаёт
   никаким полем, но для «текущее / старое» диапазонов ID достаточно.
2. **Движение запаса** (`_activity`): медиана модуля изменения количества
   между снимками, в % от типичного запаса. Товар с движением < 1%
   считается стоячим, выбрасывается из списка действий и не получает
   совет «брать».

**Что `_activity` НЕ меряет.** Мы храним свёртку стакана, а не отдельные
лоты, поэтому «продали 100 штук» и «выставили 100 штук» неотличимы —
объёма продаж отсюда не получить, и делать вид, что получили, нельзя.
Метрика отвечает на другой вопрос, ровно тот, который и нужен: рынок
шевелится или стоит. Медиана, а не среднее: одна поставка на полмиллиона
единиц иначе объявила бы мёртвый рынок живым.

Проверено на подделанной истории из 15 снимков: как только движение
измерено, список переворачивается — девять старых ловушек уходят,
остаются товары текущего дополнения с живым рынком.

### НАСТОЯЩИЕ ПРОДАЖИ: СРАВНЕНИЕ ЛОТОВ ПО id (проверено 2026-08-07)

У каждого лота в ответе есть свой `id`, и он **переживает смену снимка**:
из 17 631 лота id уцелели у 84.3%, а у 99.8% выживших совпали предмет,
цена и количество. Значит id опознаёт тот же лот, а не переиспользуется.

Отсюда измерение объёма: лот, пропавший между снимками с запасом времени
`LONG`/`VERY_LONG`, за час протухнуть не мог — его забрали. Корзины
Blizzard: SHORT <30 мин, MEDIUM 30 мин–2 ч, LONG 2–12 ч, VERY_LONG >12 ч;
считаем только две последние, остальные могли истечь сами.

**Хранить состояние НЕ НУЖНО.** Сборщик и так живёт окно в 55 минут, и
предыдущий снимок держится прямо в памяти процесса. Отрезок поэтому
удлинён с 25 до 35 минут — чтобы граница часа попадала внутрь. Складывать
17 тысяч id в git каждый час означало бы мегабайты мусора.

**Это ВЕРХНЯЯ ОЦЕНКА, а не сами продажи.** Снятие лота продавцом (чтобы
перевыставить дешевле) снаружи неотличимо от покупки, а подрезают друг
друга постоянно. Для сравнения товаров между собой годится, для обещаний
по срокам — только с оговоркой, и оговорка написана в интерфейсе.

Навар благодаря этому превратился в срок: «разойдётся за 7 ч» вместо
косвенного «движение 4.6%». Товар, чей хвост расходится дольше недели
(`MAX_HOURS_TO_CLEAR`), считается стоячим и из находок выбрасывается.

**Признак застоя обязан жить в ОДНОМ месте** (`ItemView.stalled`). Он был
продублирован внутри `bargains()`, копии разошлись при переходе на
измеренную скорость, и список находок молча опустел.

### ПОРОГ ПРОБУЖДЕНИЯ СТРОЖЕ ПОРОГА ПОКАЗА

В приложении находка от 500 з — человек сам зашёл смотреть и видит все
числа разом. Алерт приходит без спроса и требует действия, поэтому порог
10 тыс. з (`ALERT_MIN_UPSIDE`) плюс отдельное условие `_worth_waking`.

Первый сухой прогон показал, зачем: наверх вылезли «Льняная ткань» с
наваром 467 тыс. на 558 тыс. штук и «Огнецвет» на 528% — старьё с
неизмеренной скоростью. Арифметика верная, совет вредный. Будим, только
если известно, что товар расходится: скорость измерена ЛИБО это текущее
дополнение.

Тот же перекос был и в приложении: находки сортировались по одному лишь
навару, и верх занимали ловушки, вытесняя товары текущего дополнения с
честными десятками тысяч. Порядок стал двухступенчатым — сначала те, про
кого известно, что они расходятся.

### НЕДЕЛЬНЫЙ РИТМ ТОВАРОВ

`analytics/auction.rhythm` — тот же приём, что `seasonality` для жетона:
нормализация к скользящей медиане за 7 дней (без неё «ритм недели»
выродится в «на этой неделе реагент подорожал», особенно вокруг патча),
время EU-серверов, а не омское.

Два отличия от жетона:
- **нужны обе стороны.** Жетон Карен только покупает, там искали дно.
  Товары он и покупает, и продаёт — значит дешёвый час и дорогой равно
  важны.
- **пул по всем товарам.** Отклонения всех отслеживаемых сводятся в
  один набор, и ритм виден в разы раньше, чем по одному товару.

Проверено на подделанной истории с ЗАЛОЖЕННЫМ рисунком (+12% в ночь на
среду, −8% в субботу днём, плюс тренд роста): детектор вернул Ср 03–06
+12.1% и Сб 11–14 −8.1%, а тренд нормализация съела — остальные дни
вышли по нулям.

### Направление события у реагентов ОБРАТНОЕ жетону

Перед контентом дорожает и то и другое, но жетон Карен **покупает** (и
«дорого» = плохо), а реагенты может в этот пик **продать**. Поэтому фаза
`before` для жетона значит «не бери», а для аукциона — «пора продавать
запасённое». Не копировать логику вердикта жетона механически.

## ОКНО: ПОРЯДОК ВАЖНЕЕ ПОЛНОТЫ (просьба Карена 2026-08-09)

«Я не понимаю, как этим пользоваться, всё так хаотично». Секций на
вкладке аукциона стало шесть, и открывались они разом — экран начинался
с шести списков, без подсказки, что читать первым.

Лечение — не убирать содержимое, а расставить его:

1. **Свёрнутые секции** (`.fold` в style.css). Раскрыта ровно одна —
   «Что запасать под патч», у неё же единственная янтарная линия слева.
   Остальное свёрнуто. Движения нет, как и везде в KTRANS: знак `+`/`−`
   и цвет заголовка, никаких анимаций.
2. **Состояние запоминается** в `localStorage`. Без этого сворачивание
   превращается в лишний клик при каждом запуске.
3. **Свёрнутый заголовок несёт сводку справа** («12 находок», «436
   товаров», «Midnight: патч 12.1 — через 2 дн»). Иначе сворачивание
   прячет не только подробности, но и сам факт, что внутри что-то есть.
4. **Пустая секция объясняет пустоту.** «Пусто без причины» читается как
   поломка, и человек начинает искать её у себя. Крафт прямо пишет, что
   считать нечего из-за слотов качества, а не молчит.

Порядок секций сверху вниз — это ответ на вопрос «что делать»: запас под
патч → крафт → разрывы в стакане (подписаны лотереей) → ритм → полная
таблица.

**График жетона получил «сутки» и «7 дн».** Цена пересчитывается раз в 20
минут, и внутрисуточное движение (замерено: 8% за сутки) на 30-дневном
горизонте уже сглажено. Подпись при наведении сама переключается на
время вместо даты — порог `days >= 45` тот же, что у перехода на дневную
медиану.

**Побочно найден баг:** класс `.range` носили и кнопки периода, и
«обновить» на аукционе, а обработчик выбирал их всех по классу. Клик по
«обновить» уводил `state.days` в `NaN`, и график переставал
перерисовываться. Выборка сужена до `#ranges .range`.

## КОЛИЧЕСТВАМ НЕ ВЕРИМ — И БОЛЬШЕ НЕ СЧИТАЕМ ПО НИМ (2026-08-09)

Карен: «меня сбивает с толку наше ограничение в 50 000 голд, прогнозы всё
равно нереальны, товара по факту оказывается больше, чем мы видим».

Он прав, и это подтверждается нашими же замерами:

| величина | дрейф между часовыми снимками |
|---|---|
| цена (пол) | **0.3%** |
| количество | **19.8%** (у 23% товаров больше 50%) |

На «Искаженной ведунице» разошлось втрое: 4 069 шт в снимке против 12 748
в игре. Значит любая метрика, опирающаяся на количество, строит вывод на
самом шатком числе, какое у нас есть.

**Что сделано:**

- Из «Что запасать» убраны количества и бюджет. Остались цена, её уровень
  среди своих значений и изменение за окно — то, что мы знаем точно.
  Сколько брать, видно на живом прилавке.
- Секция «Разрывы в стакане» **убрана из окна**, а алерты по ним
  **отключены**. Дважды проверена золотом, оба раза сделки не
  существовало. Расчёт (`bargains`, `_plan`, `_stops`) оставлен в коде:
  если такт Blizzard ускорится, включать будет что.

**Правило на будущее: цена — факт, количество — оценка порядка величины.**
Строить на оценке главный экран нельзя, а прятать её за точными цифрами —
тем более.

## ОКНО: КЭШ WEBVIEW2 ПОКАЗЫВАЛ ПОЛОВИНУ ПРАВКИ (2026-08-09)

Карен обновил приложение и увидел странное: заголовки секций отзываются
на клик, а сворачиваться отказываются. Причина — WebView2 отдал НОВЫЙ
`app.js` и СТАРЫЙ `style.css` из своего кэша.

Симптом коварен тем, что выглядит как ошибка в логике, и человек идёт
искать её не туда. В браузере то же самое работало исправно.

Лечение — `app._drop_stale_cache()`: отпечаток по времени изменения
файлов `ui/` сверяется с сохранённым, разошёлся — кэш сносится целиком.
Не выборочно: выборочная чистка чужого кэша даёт непредсказуемо сломанный
движок.

## ТЕЛЕГРАМ ТОЛЬКО ОДНОСТОРОННИЙ (решено 2026-08-08)

Интерактивный бот (`kmarket/bot.py`, команды `/price`, `/verdict`,
`/season`, `/events`) **удалён по прямой просьбе Карена**. Причина не в
коде — он работал, — а в требовании к продукту: **на машине не должно
оставаться ни одного фонового процесса.**

Разница механик, из-за которой это вообще вопрос:
- **Алерты — это push.** Их шлёт GitHub Actions из облака, компьютер в
  цепочке не участвует. Работают с выключенным ПК.
- **Команды — это pull.** Бот сам опрашивает Telegram, поэтому требует
  постоянно запущенного процесса.

Режим `--once` под крон дал бы ответы и без ПК, но крон Actions
исполняется раз в 1–3 часа (см. раздел про крон), а ответ на «покажи
цену» через полтора часа хуже отсутствия функции. Круглосуточный бот
требует VPS, от которого Карен отказался.

**Возрождать бота без явной просьбы нельзя.** Заодно снято меню команд
через `setMyCommands` с пустым списком: иначе в телеграме висел бы список
команд, которые ничего не делают. Проверено — осталось ноль.

**Про крон Actions:** GitHub отключает расписание в репозиториях без
активности 60 дней. Сборщик коммитит сам, так что активность есть всегда —
но если сбор когда-нибудь встанет, проверять надо в первую очередь это.
